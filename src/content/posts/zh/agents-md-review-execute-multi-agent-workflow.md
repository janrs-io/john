用 AI Coding 工具写一个 Demo 页面只需要 30 秒，但一旦进入**多模块、前后端联调、有严格并发与权限约束的复杂全栈项目**，很多团队很快就会遇到四个经典失控场景：

1. **把咨询当指令，AI 抢跑改代码**：你只是问一句“这个并发锁怎么设计比较好？”，AI 直接顺手改了 6 个文件并装了新依赖。
2. **上下文腐烂与“打补丁式”屎山**：一个文件越改越大（突破 1500 行），AI 找不到全局上下文，开始在错误的方向上反复修修补补。
3. **偷懒反模式（Lazy Shortcuts）**：为了快速跑通，AI 会在前端写死 `page_size: 999` 拉全量后 `.find()`、在金额计算里裸写浮点数、或者默默吞掉 `catch {}` 异常。
4. **多 Agent 并行撞车**：两个会话同时改全局配置文件或同一个大接口文档，互相覆盖且代码风格分裂。

要真正把多 Agent 变成可控的工程生产力，不能靠每次在对话框里临时叮嘱，而需要把**规则写进仓库、用状态机锁住副作用**。下面是一套完全通用的 **“AGENTS.md 仓库宪法 + REVIEW/EXECUTE 三态门禁 + 多 Agent 协同 SOP”**。

---

## 一、用 `AGENTS.md` 立下“仓库宪法”

几乎所有现代 AI Coding 工具在启动时都会优先读取根目录的 `AGENTS.md`。它不是给人看的欢迎页，而是**给所有 AI Agent 下达的最高工程约束**。

一份有效的 `AGENTS.md` 建议包含以下五类硬性红线（可根据团队技术栈调整）：

### 1. 代码物理规模红线
- **单函数 / 单组件上限**：例如严格控制在 `300` 行以内，禁止单函数承担多重异构逻辑。
- **单文件硬红线**：业务文件舒适区在 `300 ~ 600` 行，**严禁突破 `800 ~ 1000` 行**。一旦触碰阈值，必须停下抽离 Hook、子组件或领域服务。

### 2. 禁止偷懒反模式（Anti-Shortcuts）
把 AI 最容易偷懒的坑直接写死在规则里：
- **禁止写死大分页截断**：列表选择器或外键展示，禁止写死 `page_size: 999` 一次性拉取并在前端 `.filter()` / `.find()`；必须走服务端防抖搜索与分页。
- **精度与除零熔断**：金额、汇率、物理计量禁止裸写浮点乘法，除数必须校验 `> 0`。
- **异步与边界防御**：禁止吞掉 `catch {}`，所有写操作必须覆盖 `Idle / Loading / Success / Error` 四态；禁止用 `window.alert` / `confirm` 原生弹窗。

### 3. 反直觉 `Why` 注释规范
禁止写“代码语法复述型废话注释”（如 `// increment i by 1`）。**只要求写清业务上下文、边界约束以及反直觉防坑原因（`Why:`）**。例如：

```go
// Why: detach from parent HTTP request ctx so client disconnect does not abort async outbox dispatch.
asyncCtx := context.WithoutCancel(ctx)
```

如果不写这行 `Why`，下一个接手的 Agent 很可能会觉得“为什么不直接传 `ctx`”而“好心优化”出线上 Bug。

### 4. 文档即代码（Living Docs）
架构或接口契约一旦变更，必须在同一次任务中同步更新 `docs/` 与 OpenAPI 契约，避免“代码改了三代，文档还停留在半年前”导致后续 Agent 被旧文档误导。

## 二、核心防抢跑机制：`ANSWER / REVIEW / EXECUTE` 三态门禁

防止 AI 乱改代码最有效的方法，不是靠“请不要改代码”这种口头提醒，而是建立**按副作用分类的三态交互协议**。

### 1. 三种模式与副作用判定

| 模式 | 允许动作 | 禁止动作 | 触发条件 |
| :--- | :--- | :--- | :--- |
| **`ANSWER`** | 直接回答知识性问题 | 调用任何文件、命令或外部工具 | 无需检查工作区即可回答 |
| **`REVIEW`** | 只读检查、读文件、分析、输出**变更卡** | 写/删文件、装依赖、写库、部署、`git push` | **无明确执行许可时的默认模式** |
| **`EXECUTE`** | 严格按已批准方案执行当前**单个微步** | 超出白名单、自动进入下一步、顺手修邻近问题 | 人类回复固定审批口令 |

**核心原则：按“副作用”而非“语气”分类。**
只要操作会改变持久化状态（改文件、装包、数据库迁移、重启服务、`git commit`、发请求），无论用户用的是疑问句还是感叹句，默认一律处于 `REVIEW` 模式，**严禁动手写入**。

### 2. `REVIEW` 阶段必须先交“变更卡”

在 `REVIEW` 模式下，AI 的唯一产出是先调研并输出一张结构化**变更卡**，然后停下等待审批：

```text
模式=REVIEW
方案编号：A
目标：为订单接口增加 Idempotency-Key 幂等校验中间件
允许修改的文件：
  - server/internal/middleware/idempotency.go
  - server/internal/middleware/idempotency_test.go
非目标：不修改现有订单业务逻辑与前端请求封装
计划执行的命令：go test ./internal/middleware/...
数据或外部系统影响：复用现有 idempotency_keys 表，无 DDL 变更
风险：需注意并发请求同一 Key 时的行锁竞争
验证方式：并发单元测试验证相同 Key 重放、不同 Body 报 422
本次停止点：完成中间件与单测后停止，不挂载路由
申请执行：第 1 步
```

### 3. 一次性授权口令与自动失效规则

人类审阅变更卡后，**只有回复固定格式的精确口令**才允许进入 `EXECUTE`：

```text
确认执行方案A第1步
```

单独的“可以”“好的”“开始吧”在复杂任务中容易产生歧义（特别是对话里有多个候选方案时）。而且授权是一次性的，满足以下任一条件立即失效，必须退回 `REVIEW`：
1. 当前步骤执行完成（严禁自动接着做第 2 步）；
2. 当前步骤失败（严禁 AI 自己换另一种方案擅自重试）；
3. 发现需要修改白名单之外的文件；
4. 人类补充了新需求或调整了范围。

## 三、多 Agent 协同：防撞车与防失忆

当一个项目大到需要同时推进前端、后端、接口契约和基础设施时，单对话很快会遇到上下文爆炸。可以采用 **“1 个架构师 + N 个模块 Coding Agent + 1 个独立终审官”** 的分工模式：

### 1. 角色与边界隔离
- **架构师 Agent**：负责维护 `AGENTS.md`、数据库 Schema 与模块化 `openapi.yaml`，不直接写业务 CRUD。
- **模块 Coding Agent**：**一模块一对话，验收即结束**。
  - **目录隔离**：前端限定只在 `src/features/<module>/` 内修改；后端限定只在 `internal/modules/<module>/` 内修改。
  - **契约文件拆分**：千万不要把所有 API 塞进一个上万行的 `openapi.yaml`！根目录 `openapi.yaml` 只做轻量索引，通过 `$ref` 拆分为 `openapi/common.yaml`、`openapi/auth.yaml`、`openapi/orders.yaml` 等模块文件，彻底避免多个 Agent 并行修改同一个文件导致 Git 冲突。
  - **颗粒度控制**：每个执行微步控制在等价资深工程师 **15~20 分钟手写量（约 30~80 行核心代码）**，AI 执行只需十几秒，人类 Review 只需 30 秒。

### 2. 防失忆与无缝交接（Handoff）
一旦出现以下信号，说明当前对话上下文已经污染或过载，**立即叫停，不要继续硬修**：
- 连续 2 次修改同一个 Bug 仍在打转；
- AI 开始凭空编造不存在的字段名或路径；
- 对话超过 25~30 轮，或者准备切换全新模块。

此时让老对话严格基于当前工作区真实文件输出一份《无缝交接清单》：
1. 本次已完成且验证通过的文件与功能；
2. 讨论拍板过、但还没落盘的临时约定；
3. 当前卡住的具体报错与下一步最小可执行动作；
4. 新会话开工前必读的 3~5 个关键文件路径。

然后直接开一个干净的新会话接力，上下文瞬间恢复清零状态。

### 3. 独立终审官与“Blocking vs Nit”原则
代码写完后，新开一个只读上下文的 Agent 做上线前终审，并参考 Google Code Review 的 **Blocking vs Nit** 准则：
- **只报 Blocking 阻断项**：丢数据、算错钱、越权/敏感信息泄露、并发竞态、容器无法启动、类型/测试未通过；
- **严禁输出 Nit 吹毛求疵**：禁止对命名偏好、可抽可不抽的封装、未来阶段才需要的过度设计提出阻塞意见，避免 AI 陷入“无限自我重构”的死循环。

## 四、交卷门禁：自证与 Bug 永久锁死

### 1. 交付必须附“实测自证”
AI 宣称“已完成”时，禁止只口头总结“我修改了 X 和 Y，现在应该没问题了”。必须要求在当轮输出真实执行的检查结果（如 `npm run typecheck` 0 报错、`go test -race ./...` 全部通过）。

### 2. Bug 回归永久锁死（Regression Lock-in）
每当在开发或测试中抓到一个真实 Bug（例如“并发抢占重复写入”或“边界精度丢失”），修复代码的同时，**强制要求在对应测试文件新增一条以 `REGRESSION-YYYYMM` 命名的永久测试用例**。后续无论换多少个 Agent 重构代码，只要这条回归测试还在 CI 里跑，历史错误就永远不会复发。

---

## 总结

驾驭多 Agent 协同开发复杂全栈项目，本质上不是“找一个更聪明的提示词”，而是**用软件工程的方式治理 AI 的不确定性**：
- 用 **`AGENTS.md`** 划定不可逾越的物理与质量底线；
- 用 **`REVIEW / EXECUTE` + 变更卡** 锁死副作用，消灭 AI 抢跑；
- 用 **模块化目录 + 拆分 OpenAPI + 交接清单** 隔离多 Agent 上下文，实现高确定性的并行交付。
